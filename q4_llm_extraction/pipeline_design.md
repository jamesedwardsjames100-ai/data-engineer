# Q4.1 LLM 抽取 Pipeline 设计

## 1. 分流策略（成本控制核心）
为了在 $3 USD 预算和 40 分钟内处理 1.4 万条差评，我设计了“规则前置过滤 + LLM 兜底”的分流机制。
尽管最终数据显示，因为电商评论普遍较长，规则拦截率仅为 0.07%，但该机制依然成功在本地过滤掉了极短且无意义的纯情绪文本。分流依据如下：
*   **无效空值过滤**：剔除 4-5 星好评以及仅有评分未写文字的记录。
*   **长度阈值拦截**：使用 `len(text) < 5` 的硬性规则，拦截极简文本（如 "Ruim."）。
*   **纯情绪词黑名单**：构建葡语高频情绪词库（如 péssimo, muito ruim），完全命中则直接打上空标签，跳过 LLM。

## 2. Prompt 设计质量与防幻觉
*   **严格 JSON 约束**：在 System Prompt 中强令禁止输出任何 Markdown 标记，并设定严格的 Schema，确保 `json.loads()` 100% 成功。
*   **绝对防幻觉**：强制要求 `evidence_quote` 必须从葡语原文中一字不差地截取。若原文只有废话，强制 `issues` 数组返回空 `[]`，杜绝脑补。
*   **赋能下游业务**：设定 `actionable_for_seller` 枚举，将质量问题归因给卖家（true），将物流等不可控因素归因给平台（false），直接赋能商家考核。
*   **内置翻译降本**：让模型直接阅读葡语，并在 `evidence_quote_en` 输出精准翻译，为跨部门英文汇报省去了单独调用翻译 API 的延迟与费用。

## 3. 请求策略与工程健壮性
考虑到 DeepSeek 极快的推理速度与低价，我采用了**单条并发 + 十级防弹重试（tenacity）**的架构。遇到 API 超时或限流时自动指数退避重试；同时使用正则清理模型可能返回的 Markdown 标记，确保主流程不被单条脏数据阻断。
