# Q1.3 数据清洗策略设计

### 1. 为不同下游用途设计清洗方案
*   **用途 A：销售总额统计 / 财务报表**
    必须剔除 `Invoice` 以 `C`（取消）和 `A`（坏账调整）开头的记录；剔除 `StockCode` 为 `POST`、`BANK CHARGES` 等非实体商品记录；剔除 `Price <= 0` 的异常行。
    因为财务报表只关心真实的商品交易流水，必须把退货、运费、坏账核销剥离开，否则会严重低估真实营收。
*   **用途 B：客户分群（RFM 模型）**
    必须剔除 `Customer ID` 为空的行（约 24 万行）；剔除 `Quantity <= 0` 的记录；剔除完全重复的行。
    因为FM 模型（最近一次消费、消费频率、消费金额）极度依赖精准的用户 ID。匿名用户无法追踪历史复购，保留他们只会稀释模型权重。
*   **用途 C：商品推荐模型**
    保留有效的 `Customer ID` 和 `StockCode`；剔除 `Quantity <= 0` 的记录（退货不代表正向偏好）；剔除如 `15056BL` 这种录入不规范的错乱代码（或截取前 5 位修复）。
    因为推荐模型需要构建纯净的“用户-物品”交互矩阵，负数和异常代码会造成矩阵极度稀疏，干扰推荐算法。

### 2. 哪些数据“看起来脏”但实际上不该删除？
*   **负数量的退货记录（C 单）**，因为在做全站 GMV 预测时，它们是真实的业务流水；在做供应链优化时，退货率是核心指标。如果直接 `dropna` 或删除负数，就会丢失重要的商业情报。
*   **邮费记录（POST/DOT）**，因为虽然它们不是商品，但它们构成了客户支付的真实客单价。在分析客户消费能力时，保留它们能还原更真实的交易场景。

### 3. 哪些清洗操作是有损的？如何决定？
*   删除缺失 Customer ID 的数据是严重有损的，这批数据虽然只占金额的 13.68%，但绝对值极其庞大（24 万条）。
*  如果是做用户画像/RFM，这批数据无价值，我会果断删除；但如果是做全站销售趋势、或者用无监督学习做商品聚类，我会保留它们，并用 “Unknown” 去填充 ID，或者打上“游客”标签单独分析。
