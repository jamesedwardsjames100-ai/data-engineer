# Q5.1 - 实时数据管道设计

## 📋 题目背景

Olist 当前的数据是离线 CSV 导出。现在业务需求是——卖家希望**实时**看到自己的订单情况、买家评价、物流异常。

请设计一个**实时数据架构**，满足：

- 订单状态变更后 **30 秒内** 反映在卖家后台
- 评价文本进来后 **1 分钟内** 触发情感分析 + LLM 抽取
- 物流异常（如某订单延迟超过预计时间）**自动报警**到卖家
- 历史数据查询（卖家想看过去 6 个月的成交曲线）**毫秒级响应**
- 当前数据规模：**10 万订单/天**，预计 2 年内增长到 **100 万订单/天**

要求：800-1500 字 + 一张架构图

# Q5.1 - 实时数据管道设计

## 📋 题目背景
Olist 当前的数据是离线 CSV 导出。现在业务需求是——卖家希望实时看到自己的订单情况、买家评价、物流异常。
架构演进目标：支撑订单状态 30 秒内可见、评价 1 分钟内抽取、物流自动报警、历史曲线毫秒级响应，且需应对从 10万/天 到 100万/天 的业务增长。

---

## 1. 整体架构图

### 阶段一：10 万订单/天（MVP 低成本阶段）
*   **架构描述**：不引入复杂的流处理组件。直接使用 **MySQL 主从架构 + 轻量级消息队列 (Redis Pub/Sub) + 定时任务**。
*   **业务流转**：订单库通过 Binlog 将变更同步至 Redis；卖家前端轮询 Redis 获取最新状态（30 秒内延迟可接受）；历史报表直接通过 MySQL 的 T+1 预聚合宽表读取。
*   **优势**：运维成本极低，研发周期短，满足早期业务验证。

### 阶段二：100 万订单/天（全链路实时阶段）
当数据量达到百万级，MySQL 的写入和聚合会成为巨大瓶颈，必须升级为分布式流处理架构。

```text
【数据源层】
 交易库(MySQL) ──┐
 评价库(MySQL) ──┼─▶ (Canal监听Binlog/API) 
 物流中心(API) ──┘
       │
       ▼ (毫秒级接入)
【接入层】 Apache Kafka (按 order_id 哈希分区，保证同一订单绝对有序)
       │
       ▼
【计算层】 Apache Flink (实时流计算核心)
       ├─▶ [流1: 订单状态流] ──(30秒内)──▶ 写入 Redis
       ├─▶ [流2: 评价分析流] ──(规则分流)──▶ 异步调 LLM ──(1分钟内)──▶ 写入 ClickHouse
       └─▶ [流3: 物流CEP流] ──(超时匹配)──▶ 触发 钉钉/Webhook 报警
       │
       ▼
【存储层】
 ├─ Redis (KV缓存)：卖家实时看板数据 (支撑超高并发读)
 ├─ ClickHouse (OLAP)：历史全量明细 & 评价结构化数据 (列式存储，聚合极快)
 └─ MySQL (OLTP)：最终订单持久化落库
       │
       ▼
【应用层】 卖家后台 (WebSocket 实时推送 / HTTP 查 ClickHouse 曲线)

## 2. 数据存储选型

> 哪些数据进 OLTP、哪些进 OLAP、哪些进消息队列、哪些进缓存？为什么？

OLTP 数据库存核心业务主数据，进当前的订单表、用户表、卖家表。因为OLTP 具备强事务一致性（ACID）和行级锁。买卖交易、扣减库存等核心动作，必须保证数据绝对正确，绝不能丢。但它的短板是遇到复杂的海量聚合查询会直接卡死，不适合做分析。

OLAP 数据库存历史明细与预聚合宽表，进过去 6 个月甚至更久的订单历史明细、评价标签宽表、每日预计算的成交额。因为OLAP 采用列式存储和向量化执行，极其擅长在海量数据（百亿级）中进行多维聚合统计。卖家想看过去 6 个月的曲线，在 OLAP 里查询只需毫秒级，而在 OLTP 里可能要跑几分钟。

消息队列存变更事件流，进MySQL的Binlog、用户新提交的评价文本、第三方物流回调的轨迹。因为削峰填谷与系统解耦。面对 100 万/天的订单，直接用代码同步调用下游（如写数据库、调 LLM）会瞬间压垮系统。Kafka 作为高吞吐的缓冲带，不仅能把突发流量平滑处理，还能让下游系统按自己的节奏消费，互不影响。

缓存存热点数据与实时计算结果，进卖家后台首屏显示的最新订单状态（已发货、已签收）、未读评价数、排行榜。因为内存读写，极速响应。业务要求 30 秒内看到状态变更，如果让前端直接查 MySQL，高并发下数据库会崩溃。将实时流计算（Flink）算出的最新结果写入 Redis，前端直接读内存，轻松支撑上万的 QPS。

## 3. LLM 部分如何避免成本失控

> 100 万订单/天，如果每条评价都过 LLM，年成本估算多少？怎么优化？

成本估算（以最坏情况为例）：
假设 100 万订单/天，其中 30% 产生了评价（即 30 万条/天）。每条评价包含 Prompt、原文和输出 JSON，平均消耗约 450 个 Token（输入 300，输出 150）。

如果头铁全量用 GPT-4o（输入 $5/1M tokens，输出 $15/1M tokens）：
单条成本 = (300×$5 + 150×$15) / 1,000,000 = $0.00375。
日成本 = 30万 × $0.00375 = **$1,125 / 天**。
年成本 = $1,125 × 365 = 约 $41 万美元（折合人民币近 300 万）。这显然是不可接受的。

优化方案（将年成本打至 1 万美金以内）：

“漏斗式”规则前置过滤（省 50%）：
在进入 LLM 之前，先用正则表达式或停用词表过滤掉 50% 的垃圾短评（如“bom”、“ruim”）。这部分不花钱，直接打标签。

模型路由 （省 90%）：
绝对不用 GPT-4o 处理全量数据。将剩余的 15 万条数据切换至 DeepSeek-V3 或 GPT-4o-mini（输入约 $0.15/1M，输出约 $0.6/1M），单条成本降至 $0.000135。此时日成本约 **$20/天**，年成本降至 $7,300。

异步微批处理（再省 40%）：
System Prompt 是很长的（包含 Few-shot），如果单条调用，每条都要重复付一遍 System Prompt 的钱。通过 Flink 攒批（如 20 条打包成一次请求），可以极大地摊薄 System Prompt 成本，且能利用大模型厂商提供的 Batch API（通常半价）。

结果缓存与去重：
电商评价中存在大量高度相似的模板（如“物流太慢了”），利用 Redis 或向量数据库做语义去重，相同的问题直接复用历史抽取结果。

离线错峰处理：
除了需要实时报警的极端差评外，大部分评价的抽取可以放在凌晨低峰期进行，甚至部署本地开源小模型（如 Llama-3-8B）跑通宵，彻底将 API 成本降为服务器电费。

优化后结论：通过规则过滤 + 模型降级 + 批处理，每天的 LLM 成本可控制在 $10 ~ $20，全年成本不超过 $1 万美金，完美兼顾了业务体验与 ROI。

## 4. 三个最大的风险点和应对方式

### 风险 1：

**说明**：Flink 处理速度跟不上（背压），导致 30 秒 SLA 被打破。

**应对**：局限性：如果发生大促，或者下游写 Redis 变慢，Kafka 消息会严重积压。

降级预案：

监控 Kafka 的 Lag，动态增加 Flink TaskManager 扩容。
熔断降级：若算力耗尽，立刻通过配置中心下发指令，暂停“评价分析流”和“物流CEP检测”，将 100% 算力集中给“订单状态流”，保住核心交易体验。

### 风险 2：

**说明**：ClickHouse 写入瓶颈。

**应对**：局限性：ClickHouse 极度反感高频单条写入，频繁 Merge 会导致数据库卡死。

降级预案：

微批写入：Flink 侧必须设置 5 秒窗口或 1000 条的 Batch 阈值，攒批写入。
查询降级：若 ClickHouse 节点故障，后台“历史曲线”接口立刻降级，改读 MySQL 中 T+1（前一天）的离线报表，并在前端提示“数据延迟”，保证应用不白屏。

### 风险 3：

**说明**：外部 LLM API 超时/限流，拖垮主链路。

**应对**：局限性：大模型 API 极不稳定，若发生超时重试，会占满 Flink 线程池，引发雪崩。

降级预案：

异步隔离：严格使用 Async I/O，超时即丢弃，不阻塞主流程。
死信队列（DLQ）：调用失败的评论文本推入 Kafka 的 llm_failed_topic，由凌晨的离线任务慢慢补偿重试。
多供应商路由：代码层集成两家大模型，一家超时率超 5% 自动熔断，切到另一家。

## 5. 关于业务规模变化的考虑

> 10 万订单/天 vs 100 万订单/天，架构会有什么不同？

10 万/天（起步期）：直接上 Kafka + Flink 完全是“杀鸡用牛刀”，成本高且运维极难。此时应该采用：MySQL 主从 + Redis Pub/Sub + 定时 Python 脚本。历史曲线用 MySQL 宽表预聚合即可搞定。

100 万/天（爆发期）：数据量涨 10 倍，单机 MySQL 绝对撑不住。此时必须引入 Kafka (削峰) + Flink (流计算) + ClickHouse (OLAP分离)。

设计理念：架构是演进出来的，不是一开始就设计出来的。如果业务增长，必须提前 3 个月进行压测评估，在 MySQL 出现 IO 瓶颈前，平滑切入 Kafka/Flink 集群。
